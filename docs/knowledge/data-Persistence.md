# 数据持久化

## Playerprefs

学完了 C#基础后，就开始接触数据存储功能
Playprefs 虽然简单，就是 string,bool,int 这三种类型通过唯一 key 进行存储和读取

但是课程还是特别深入的，存储还能理解，但后续读取如同用反射自己做了给反序列化工具，让 99%的变量都能依据其名称进行读取，导致其 string key 的十分长，例如我这里注册表有参数为 Player1_PlayerInfo_Dictionary 2_ItemDict_Value_1_ItemInfo_String_name_h888815756

> 代表就是名称为 Player1 的 PlayerInfo 的类里面，存储了一个 ItemDict 的字典长度为 2，其中 int 值为 1 的 ItemInfo 的 value 的名称为 h888815756（这里采用了加密）
> 课程使用了递归+反射，导致 Playerprefs 简单但课程质量高，我能理解并且跟上，但是难以独立写出来这种管理器功能

- 最后是跟着课程制作了一个 Playprefs 的数据管理器

## Json

Json，知识点少，API 自动读取类存储类，大概内容就是了解 API，而且看 json 文件也能读懂也会自己配置，缺陷是无法存储字典类型

后续增加了 LitJson 插件，不仅仅支持数据集的存读，字典也能进行，但是缺点依旧存在，因为 json 文件本身的格式问题，key 都是默认 string，需要统一规范，而且因为反序列化顺序所以使用 LitJson 需要保留空的构造函数

- 最后以此不同的优缺点创建了一个 Json 数据管理器，而且调用时通过枚举去选择使用序列化和反序列化的方式为 Json 还是 LitJson

## 二进制存储

二进制，难也不难，序列化和反序列化的实现很简单，早早实现了相关的功能和单独的二进制数据管理器，更多的是学了是关于文件的操作和状态判断，还有 Excel 转数据工具

最终整合之前的知识，创立一个 Excel 功能，结合文件操作状态判断，通过相应 Excel 格式规则，把 Excel 表的内容自动生成一个类和容器类

- 实现了二进制存储的数据管理器和自动化生成类工具

## Protobuf 序列化

当初学，不明所以，现在回顾，难也简单，现在的我觉得它和反射知识的处境差不多（知识简单，实现简单，不知道功能的实践用途，但是未来有大用处）
单论知识，使用几个 API，然后按照规则编写相关类的结构，生成一个自动化的类，用起来感觉就是用插件生成一个自动化类，按照个人开发效率和知识展现，甚至不如《二进制存储》里面的 Excel 自动生成类+二进制数据管理器

**但重点是，此课程是接着 UDP 通信的实践，实践让我看到 Protobuf 能把一个类转化的 byte[]压缩成原有 30%-50%，所以商业化内容必选它，流量成本大减**

> 附言：一个月之后我巩固网络开发，后续学习所谓的 NetMsg 和 CMD 结构才发现，它能完全忽略空引用，传递 byte[]长度实际上可以更小，达到 30%以下

## ScriptableObject

- 可视化配置 — 策划/美术可以直接编辑
- 保持引用 — 不丢失 Unity 对象关系
- 设计期存在 — 成为项目资产的一部分
- 运行时共享 — 多个系统访问同一数据源

**外挂怎么办？** 采用数据分离，SO 并不存储真正的数据，而是资产为主：

- 客户端 SO：名字、图标、特效、声音、模型
- 服务器数据：伤害、CD、价格、成功率、成长数值

### 个人对数据持久化理解

在单机上，与数据相关使用二进制或者 Json、ScriptableObject，比如玩家进度、背包数据、某关卡出怪速度和怪物数值，用于资产引用和测试时最方便（可视化 + 随意更改）。PlayerPrefs 则是音量大小、亮度等——明显区别是，网络游戏中换了设备就重置的设置，大多用 PlayerPrefs 存储。

| 数据归属 | 存储方案 | 例子 |
| -------- | -------- | ---- |
| **属于这台设备** | PlayerPrefs | 键位设置、画质选项 |
| **属于这个玩家** | 二进制/JSON | 等级、装备、进度 |
| **属于这个游戏** | ScriptableObject | 角色设计、关卡模板 |
